## 先看你能观察到的过程

假设你让 Aster 修复日期导出的跨月错误。
你提供目标、文件范围和验收条件。
模型先读取代码，再提出修改。
工具执行修改，测试产生检查结果。
Core 核对执行依据，再决定能否结束。

<SeeCodeDiagram name="architecture" />

图中的“模型”指生成下一步建议的服务。
“工具”指读取文件、修改文件和运行命令的能力。
“宿主”指使用 Core 的应用。
终端、桌面和自己的 Rust 程序都属于宿主。

## 用三个问题读懂内部结构

| 你要了解什么 | 阅读入口 | 阅读后的具体收获 |
| --- | --- | --- |
| 模型为什么这样工作 | [系统提示词](./system-prompts/) | 看见默认文本、宿主插槽和运行契约 |
| 一次任务如何执行 | [执行循环](./execution/) | 区分提案、权限、效果和事实 |
| 任务为什么还在继续 | [长期任务](./long-running/) | 读懂计划、等待、预算和切片 |
| 重启后还能接着做什么 | [恢复](./recovery/) | 区分日志重放与重试操作 |
| 何时才算完成 | [完成判定](./completion/) | 核对修改摘要、验证和资源收尾 |
| 模型为什么漏看一段材料 | [上下文](./context/) | 查看来源替换、去重和预算 |

## 先拆开，再沿任务流阅读

<SeeCodeDiagram name="meta-harness" />

拆解图中的层是职责层。
层间距离不代表进程、线程或机器。
底层检查仍然约束上层组件。
替换系统提示词，也会保留工具权限判定。

沿用同一个修复例子：

1. 打开[提示词章节](./system-prompts/)。
2. 对照[上下文装配](./context/)。
3. 跟随[单次运行](./execution/)。
4. 检查[完成依据](./completion/)。
5. 阅读[分轮执行](./long-running/)。
6. 核对[中断后的恢复](./recovery/)。

## 读源码时保留四种身份

| 身份 | 表示什么 | 为什么需要区分 |
| --- | --- | --- |
| Session | 一段持续的会话 | 目标与记录跟随原会话 |
| Run | 一次接纳的执行 | 控制命令必须指向准确的运行 |
| Tool call | 一次具体调用 | 确认回答必须绑定原参数 |
| Goal | 跨多轮的目标 | 一次 Run 结束后仍可能有未完成步骤 |

源码漫游直接提取本版提交中的代码。
高亮行表示当前入口，左侧行号保留仓库位置。
「阅读全部源码」支持连续对照各站内容。
正文中的源码链接支持继续追踪调用方。

## 示例与实际记录怎样区分

本组章节用日期导出修复说明执行顺序。
示例没有启动模型，也没有产生真实工具记录。
状态名、接口名和源码片段来自本版实现。
实际任务的结论仍以该次运行的事实为准。
