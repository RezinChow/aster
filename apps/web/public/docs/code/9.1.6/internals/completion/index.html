何时才能说任务完成

完成门禁的真实顺序、修改摘要、验证合同、豁免、资源结清与目标完成。

最终答复要接受代码中的检查

模型给出最终答复后，Core 核对该次运行的依据。 检查结果决定运行是否支持结束。 文字中的“测试通过”不能生成通过报告。 旧报告也不能自动覆盖后来的修改。

真实判断顺序决定哪些捷径无效

次序检查对象未满足时的结果
1未解决的工具效果Incomplete
2仍阻止成功的外部观察Continue 或 Incomplete
3未观察的工作区子任务Incomplete
4修改观察是否完整Incomplete
5是否存在工作区修改无修改时支持 Narrative
6当前摘要是否有宿主豁免匹配时支持 Waived
7当前摘要是否有通过报告匹配时支持 Verified
8仍缺少依据Incomplete，并说明下一步

前四项发生在无修改判断之前。 无修改的运行也必须清除前置缺口。 一个结果不明的外部操作仍可能阻止完成。

修改摘要为什么必须精确绑定

修改账本保存该次运行观察到的工作区影响。 摘要代表当前这组影响。 验证报告需要绑定这份摘要。 模型继续修改文件后，应重新核对报告绑定。

例如，日期函数已通过跨月测试。 模型随后又修改格式化逻辑。 旧报告证明旧状态通过检查。 新的内容需要对应的新依据。

验证合同、报告和豁免是不同对象

对象谁提供含义
Verification contract宿主准入声明检查命令和覆盖范围
Verification report受控检查路径记录本次检查及所绑定摘要
Completion waiver宿主或用户明确接受对指定摘要接受验证缺口

合同声明“应该运行什么”。 报告说明“本次实际检查了什么”。 豁免说明“接受哪一份尚未验证的修改”。 模型无法仅凭生成一段文本创建有效豁免。

四个终态应怎样显示

状态准确含义容易造成的误解
Narrative无修改，且前置缺口已清除不是“代码通过了测试”
Verified当前摘要有匹配的通过依据不代表所有可能缺陷都已排除
Waived当前摘要得到明确豁免不代表验证通过
Incomplete仍有明确缺口不等同于用户暂停

宿主应显示具体缺口。 只显示“失败”会丢失后续处理所需的信息。

完成判定与资源结清怎样配合

完成门禁检查任务证据。 资源作用域管理该次运行所属的进程、工具和资源。 宿主还要等待所属资源完成收尾。 模型文本、门禁结果和资源终态分别记录。

这一区分在取消时尤其重要。 停止生成后，工具可能仍在协作退出。 界面应保留取消中的状态，直到原资源结清。 资源设计见验证与资源寿命。

长期目标还有额外的完成条件

一次 Run 的 Verified 只说明该次修改的检查依据。 目标还要接受每个计划步骤。 最后一步还要覆盖目标自身的接受条件。 全部等待与全部切片也要结清。 实现：目标完成条件 L34 ↗。

面向宿主的排查顺序

  1. 读取原始完成门禁消息。
  2. 核对未决效果与外部观察。
  3. 检查子任务的工作区影响。
  4. 核对修改观察是否完整。
  5. 对照当前修改摘要。
  6. 检查报告或豁免的绑定。
  7. 核对资源结清状态。
  8. 读取目标的当前完成条件。

完整依据来自原始运行记录。 界面文案应忠实反映该次结果。
