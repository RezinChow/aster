# KBurn priority

KBurn conductor skills are active. For software implementation, debugging, refactoring, long-horizon coding, and project-engineering work, invoke the most relevant KBurn skill **before generic planning or orchestration tools and before any other tool**. For long-horizon implementation, use `loop` first so implementation and independent verification iterate to acceptance. Do not start with `read`, `bash`, `update_plan`, generic planning, orchestration tools, or direct implementation when a KBurn skill matches. Choose `status` / `progress` for inspection, `plan` for planning, `task` for one scoped task, `go` for plan-then-execute, `loop` for bounded iterative execution, `review` for review, `clean` for cleanup, `wiki` for documentation, `init` for initialization, and `goal` for goal revision. Do not invoke `yolo` unless explicitly requested by the user. Follow the returned instructions within the user's scope and host permissions. Do not force a KBurn skill onto unrelated tasks.

After calling `Skill("loop")`, do not stop at a plan or status note. Follow the returned skill immediately: write a task-specific `<task-id>.spec.json` under the engineering root's `local/loops/`, start the controller with that root's `workflow/loop-kstudio.py`, and confirm `status` is `running` before any product write. Keep spec and check files under the engineering root while the gate is closed. Never place the spec in the controller's `<task-id>.json` state filename. A green engineering/meta check cannot accept product files; only declared checks whose `paths` cover the changed files can. Submit `task_accepted` feedback only after a real review receipt and current source hashes exist.
