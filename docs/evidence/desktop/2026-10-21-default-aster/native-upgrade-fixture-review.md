# Read-only ToYou upgrade fixture review

No app was launched and no updater operation was triggered during this review.

The existing `.tmp/studio-native-direct/StudioLegacyFixture` is a real native executable compiled from baseline commit `eb17c6ce5aa4c9ef785c12d56515e146866b1506` with a synthetic package version `2.1.2`. The build receipt is `../2026-10-21-work-alignment/legacy-native-fixture-build-r2.json`. It is not a historical published binary. Its old updater can download the complete ZIP route and replace/relaunch a `.app`; it predates the new generation/signature validation, so successful upgrade with this fixture cannot prove that historical signed distributions had the same behavior.

A minimal controlled procedure for the parent is:

1. Allocate a fresh repo-local fixture root and a never-used ToYou instance, then run the existing `target/evaluations/studio-work-alignment/native-gui-fixture.py serve --root <owned-root> --tenant toyou --instance <new-instance>`. It refuses an existing profile and writes only a fixed synthetic member record plus three device preference values. Do not use `--anonymous`; anonymous belongs to Aster. Read only that newly created `launch.json` to obtain its exact profile and environment. The owned profile is `~/Library/Application Support/dev.a3s.studio/toyou/instances/<new-instance>`; the old and new ToYou source schemas retain that same path when no legacy flat directory exists. Do not override HOME.
2. Use an owned temporary `.app` under the fixture root for the old native executable. Keep the executable inside `Contents/MacOS`; that is the old `is_app_executable` predicate. Ensure its Info plist launches that executable and declares synthetic version 2.1.2. Supply the current ToYou renderer through a separate loopback static server and `STUDIO_RENDERER_PORT` because this old fixture was built with debug assertions and opens the external renderer. The old tenant loader still uses explicit `A3S_TENANT_SLUG=toyou` and checkout branding. An assembled fixture must be labeled synthetic rather than a sealed released generation; do not relabel its stale resource manifest as valid after swapping the host.
3. Copy only the final, complete, independently verified ToYou update ZIP to `<owned-root>/release.zip`. Write `<owned-root>/release.json` with `version`, `notes`, `file_name`, exact ZIP `sha256`, `size_bytes`, and `published_at`. Version must be strictly newer than 2.1.2. The fixture serves `{success:true,code:0,data:<release.json>}` at `/v1/api/admin/app-releases/current` and the exact bytes at `/current/file`; missing files correctly return 404. It ignores the query only within this loopback mock, not in product code. Never publish that fixture metadata externally.
4. Launch only the owned old app with the exact launch environment, including `A3S_STUDIO_INSTANCE`, `A3S_ORG_API_ORIGIN`, gateway origin, explicit `STUDIO_RUNTIME_FILE`, and isolated agent home/state. Record the old process path/version, synthetic profile sentinel hashes, local preferences, and only owned session/file marker hashes. Do not print bearer credentials. Preflight that the release bundle identifier is not already running in an unrelated user's app; the old relaunch uses plain `open` and must not be allowed to route into another running installation.
5. Drive the actual update check/download/install controls with CUA. The old native updater validates the archive SHA/size, extracts one `.app`, replaces only its current owned bundle, and waits for the old PID to exit before `/usr/bin/open` of that same app path. The installed `open(1)` manual explicitly states applications inherit environment variables, so the dedicated instance should survive; verify its actual new runtime descriptor and profile, do not assume it. Its old relaunch removes the backup without checking launch success, so new native rollback tests do not turn this older fixture into a rollback proof.
6. Require the replacement host, ACP, Office, renderer, tenant brand, skill inventory/tree, and delivery manifest to match the final target ZIP generation. Verify `codesign --verify --deep --strict <owned-app>` and the generation checker before declaring success. Observe the new window/version in CUA and read its actual private runtime/plane state only to verify identity and synthetic saved state. The new host must use ToYou, never Aster or a default user profile, and retain the synthetic sentinel/preferences/session. Preserve screenshots plus old/new owned bundle hashes and runtime PID evidence.
7. Stop and clean up only recorded owned PIDs, the fixture's app/staging paths, and the newly created instance profile. Do not stop or overwrite an unrelated installation or primary profile. Keep the final package and evidence receipts.

The newest updater also has a maintained positive for a future inventory adding a resource and another removing a reference, with the full target generation resealed. This is separate from the baseline-client upgrade exercise and prevents fixing the current skill gap by permanently locking the next update to the old resource list.
